## 核心组件

### 1. Event（事件）

**职责**：定义事件的数据结构和类型

**关键类**：
- `Event`：事件基础接口
- `BaseEvent`：抽象基类，提供默认实现
- `EventType`：事件类型接口
- `EventPriority`：优先级枚举
- `EventCategory`：事件分类枚举

**设计原则**：
- 使用密封类(sealed class)限制事件类型
- 每个事件都有唯一ID和时间戳
- 支持元数据扩展

### 2. EventQueueManager（队列管理器）

**职责**：管理事件队列、调度和执行

**核心功能**：
1. **优先级队列**：使用`PriorityBlockingQueue`按优先级排序
2. **事件去重**：基于事件签名防止重复处理
3. **防抖/节流**：时间窗口控制
4. **批量处理**：收集多个事件一起处理
5. **依赖管理**：支持事件间依赖关系
6. **重试机制**：失败自动重试，指数退避
7. **超时控制**：限制处理时间

**并发安全**：
- 使用`ConcurrentHashMap`存储处理器和状态
- `Collections.synchronizedSet`管理已处理事件
- 协程+通道模式处理事件流

### 3. ExecutionStrategy（执行策略）

**职责**：定义事件如何被执行

**策略类型**：

| 策略 | 说明 | 使用场景 |
|-----|------|---------|
| Immediate | 立即执行 | 关键业务事件 |
| Sequential | 顺序执行 | 需要保证顺序的操作 |
| Priority | 优先级 | 多优先级混合场景 |
| Delay | 延迟执行 | 定时任务 |
| Batch | 批量执行 | 埋点数据批量上报 |
| Debounce | 防抖 | 搜索输入、窗口resize |
| Throttle | 节流 | 滚动事件、按钮点击 |

**扩展性**：实现`ExecutionStrategy`接口即可自定义策略

### 4. EventHandler（事件处理器）

**职责**：处理具体的事件逻辑

**类型**：
- `EventHandler<T>`：挂起函数接口，返回`EventResult`
- `EventListener<T>`：简单监听接口，无返回值

**结果类型**：
- `Success`：处理成功
- `Failure`：处理失败（触发重试）
- `Skipped`：跳过处理
- `Retry`：请求重试

**装饰器模式**：
- `filter()`：条件过滤
- `retry()`：重试逻辑
- `timeout()`：超时控制
- `combine()`：组合多个处理器

### 5. Compose Integration（Compose集成）

**职责**：提供声明式API和生命周期管理

**核心API**：

#### 观察类API
```kotlin
ObserveEvent<T>()          // 监听事件
collectEventAsState()      // 收集为State
rememberQueueState()       // 队列状态
```

#### 注册类API
```kotlin
RegisterEventHandler()     // 声明式注册处理器
```

#### 分发类API
```kotlin
rememberEventDispatcher() // 获取分发器
```

#### 修饰符API
```kotlin
clickableWithEvent()      // 点击+事件
longClickableWithEvent()  // 长按+事件
doubleClickableWithEvent() // 双击+事件
swipeableWithEvent()      // 滑动+事件
```

**生命周期管理**：
- 使用`DisposableEffect`自动清理
- `LifecycleEventObserver`感知生命周期
- 最小活跃状态控制

### 6. Logger（日志系统）

**职责**：记录事件流转过程

**分层设计**：
- `EventLogger`接口：统一日志接口
- `DefaultEventLogger`：基于Android Log
- `CompositeEventLogger`：组合多个日志器
- `NoOpEventLogger`：空实现

**日志级别**：VERBOSE < DEBUG < INFO < WARN < ERROR < NONE

## 关键设计决策

### 1. 为什么使用PriorityBlockingQueue？

**原因**：
- 自动按优先级排序
- 线程安全，无需额外同步
- 支持阻塞操作

**替代方案**：
- 普通Queue + 手动排序：性能较差
- Channel：难以实现优先级

### 2. 为什么使用协程而不是线程？

**优势**：
- 轻量级，可创建大量协程
- 结构化并发，易于管理
- 挂起函数，自然的异步API
- 与Compose深度集成

### 3. 为什么事件去重使用HashSet？

**考虑**：
- 简单高效，O(1)查找
- 同步Set保证线程安全
- 内存占用可控

**改进空间**：
- LRU缓存限制内存
- 时间窗口自动清理

### 4. 为什么使用CompositionLocal？

**优势**：
- Compose官方推荐方式
- 自动传递依赖
- 支持局部覆盖

**替代方案**：
- 单例：灵活性差
- 参数传递：层级深时繁琐

## 性能优化

### 1. 队列容量限制

```kotlin
queueConfig {
    maxSize(1000)  // 防止内存溢出
}
```

### 2. 事件去重

避免重复处理相同事件，减少计算开销

### 3. 批量处理

```kotlin
BatchStrategy(
    batchSize = 10,
    timeWindowMs = 1000
)
```

将多个事件合并处理，减少I/O操作

### 4. 懒加载

处理器按需注册，不会预加载所有逻辑

### 5. 结构化并发

使用`SupervisorJob`，一个协程失败不影响其他

## 安全考虑

1. **线程安全**：所有共享状态使用并发安全集合
2. **异常隔离**：使用`SupervisorJob`防止级联失败
3. **超时保护**：防止处理器卡死
4. **内存限制**：队列容量上限
5. **资源清理**：生命周期感知，自动释放

## 未来优化方向

## 总结

EventManager采用分层架构设计，各组件职责明确、松耦合。通过策略模式、装饰器模式等设计模式，实现了高度的可扩展性和灵活性。深度集成Compose和协程，提供了现代化的声明式API。整体设计简洁清晰，易于理解和使用。
